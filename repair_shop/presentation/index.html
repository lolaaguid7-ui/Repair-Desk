The problem / 02

Paper records make repair progress difficult to follow.

Scattered information

Customer details, device problems, and technician assignments can sit in different records.

Staff must search before answering a simple status question.

Unclear payment history

Partial payments require a reliable running balance.

Missing or repeated entries can create confusion at collection.

The design goal: one traceable order with a clear status and balance.

Problem scenario motivating the project. No field study or measured business savings are claimed.

  • The project addresses a practical workflow problem. A small shop may use paper or separate files to record repairs.
  • That makes it difficult to connect the customer, the device, the technician, and the payment history.
  • For example, a customer may pay a deposit today and collect the device later. The shop needs to know the remaining amount.
  • These are the problems that guided my requirements. I have not yet measured their frequency in a real shop.

  • Repair Desk stores the main information in one place. Each order belongs to a customer and can be assigned to a technician.
  • The dashboard summarizes the repair statuses, collected payments, and outstanding balances.
  • The user chooses CNY or USD before creating the first order. The system then keeps one currency and does not convert currencies.
  • This version is for one user on one computer. It does not need an AI service or a paid API. The local server must be running to open the app.

Relationships and constraints

Customer 1 → many Orders
Technician 1 → many Orders
Order 1 → many Payments

Exact money arithmetic

CNY 150.50 = 15050 minor units

Integer storage avoids floating-point rounding in balances.

Four main business entities, plus internal settings and submission-receipt tables.

  • The browser handles presentation. Flask receives requests and applies business rules. SQLite stores the records on the same computer.
  • I chose SQLite because this version has one local user and does not require a separate database server.
  • There are four main business entities. One customer can have many orders. One technician can handle many orders. One order can have many payments.
  • Money is stored as integer minor units. For example, 150 yuan and 50 fen is stored as 15050. This prevents floating-point rounding problems.
  • Database transactions keep related changes consistent. Submission tokens prevent duplicate orders or payments when the same request is retried.

Current boundaries: one local user, manual backups, no cloud sync, no electronic payment processing.

  • The main value is clear and connected records. The shop can look up an order and see both its repair status and its payment balance.
  • Validation also supports consistency. For example, the application rejects overpayments and prevents delivery before full payment.
  • I have not measured financial return or time savings. A useful next evaluation would ask a user to complete realistic tasks and record task time and mistakes.
  • Future improvements could include printed receipts, automatic backups, and spare-parts inventory.
  • Mobile access is a possible future extension. It is not implemented now and would need additional deployment and access-control work.
